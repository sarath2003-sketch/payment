# COMPLETE PORTAL FEATURE SPECIFICATION

This project is the existing portal. Integrate the following features into this same project rather than creating unrelated projects.

## Existing functionality to preserve
- Existing registration
- Existing login
- Existing admin portal
- Existing member system
- Existing payment functionality
- Existing chat functionality, if present

## Member and registration
- Registration data must persist in the real backend/database.
- Member IDs must be generated by backend/database; preserve sequential IDs beginning at 101 if that is the existing requirement.
- Registered members must appear in Admin > Members.
- Members must be able to log in with their actual stored credentials/ID.
- Prevent duplicate form submissions.
- Detect possible duplicate members by relevant fields and let admin review rather than silently deleting.

## Member profile
Profile page for logged-in member:
- Profile photo
- Member ID
- Name
- Phone
- Email
- UPI ID
- Registration date
- Activation status
- Payment status
- Edit appropriate profile fields
- Upload/change profile photo
- Changes must persist in database.

## Admin member management
Admin:
- Dashboard
- Total/active/inactive/pending member counts from real DB
- Search/filter/sort
- View member details
- Add member
- Edit member
- Activate/deactivate
- Soft-delete/restore where appropriate
- Duplicate-member review
- Member profile details
- Admin activity/audit log

## Activation
Statuses:
- Pending
- Active
- Inactive
- Rejected

## Payments
Admin can:
- View/add/edit/delete or correct payment records
- Update payment status
- Link payment to correct member
- Statuses: Pending, Paid, Partially Paid, Failed, Cancelled

## Live chat groups
Members > Chat Rooms:
- Create group request with group name
- Main admin approval required before group is visible
- Group requester becomes group owner/admin after approval
- Main system admin is not automatically the group admin
- Maximum 12 active members per group
- Join/leave group
- Prevent duplicate membership
- Group admin can mute/unmute/remove members
- Members can self mute/unmute
- Group admin can transfer group ownership
- Online member count
- Profile photos and member IDs
- Real-time text messages
- Emoji
- Image sharing
- Real-time join/leave/mute/unmute/message events
- Group statuses: Pending, Active, Rejected, Full, Inactive

## Admin chat management
- Pending group requests
- Approve/reject
- View groups
- Deactivate/delete where appropriate
- View group owner and member count

## Notifications
User notifications:
- Registration success
- Activation update
- Payment update
- Profile update
- Group approval/invitation

Admin notifications:
- New registration
- New group request
- Pending payment
- Possible duplicate

## Dashboard and UI
- Professional responsive design
- Reduce excessive bright yellow
- Light/Dark/System theme if compatible
- Smooth, subtle animations
- Page/card transitions
- Button hover
- Loading skeleton
- Success/error states
- Mobile responsive layouts

## Animation asset
The supplied project ZIP may contain a holographic login/animation implementation. Reuse its existing assets/components where appropriate. If an additional animation/logo asset is uploaded later, integrate that asset rather than replacing it with an unrelated animation.

## Reliability requirements
Every API-driven page must have:
Loading -> Success / Empty / Error.
Never leave infinite loading.

Trace and fix:
Registration -> API -> backend -> DB -> Admin API -> Admin list
and
Registration -> DB -> Login -> User profile.

Do not use static/demo member data to mask backend/database failures.

## Security
- Backend authorization for admin operations
- Members cannot access other members' private profiles by changing IDs
- Do not expose DB credentials
- Validate uploaded images
- Validate request payloads
- Do not return raw server/database errors to normal users

## Implementation rule
Do not rebuild the whole application unnecessarily. Inspect the current architecture and integrate these features using its existing framework, components, database conventions, and authentication where possible.
